# Рішення по бекенду (DECISIONS)

Формат: дата — рішення, потім «Чому». Нові записи додаються в кінець.
План — `docs/backend/PLAN.md` (сесії BE-S01…BE-S17, +беклог 18–20).

## 2026-10-28 — проблема дизайну: один застосунок на п'ять доменів

`INSTALLED_APPS = ['education']` (`math_world/settings.py`). Один `models.py`
(622 рядки, 23 моделі) і один `api.py` (367 рядків) обслуговують:

1. **Каталог** — навчальний контент: `Subject, Grade, Textbook, Section, Paragraph,
   Item, ContentBlock, Exercise, SubExercise, Answer, Figure, ImportRun,
   TheoryPractice`
2. **Гра/прогрес** — `Player, Attempt, LessonProgress`
3. **Школи/класи** — `School, SchoolMembership, SchoolClass, SchoolClassStudent`
   (додано FE-0640/0645, щойно)
4. **Ручна перевірка** — `ManualEdit`, `review.py`, `views_review.py`
5. **PDF-пайплайн імпорту** — `education/pdf_pipeline/` (без моделей, уже добре
   модуляризований усередині — не є частиною цієї проблеми)

Чому це проблема: нові фічі (режим вчителя, класи) додаються в той самий
`models.py`/`api.py`, що й каталог і гра, хоча логічно не перетинаються з ними.
`api.py` серіалізує JSON вручну (`figure_dict`, `exercise_dict`, `block_dict`…)
замість явного шару — контракт API (`mock/README.md`) живе в коді, розкиданому
по одному файлу разом із view-функціями.

## 2026-10-28 — карта зовнішніх ключів (чому саме такий порядок винесення)

Побудовано з `education/models.py`:

- **`School*` (4 моделі) — нуль FK у каталог.** Єдині зв'язки — на `auth.User`.
  Найбезпечніший кандидат на винесення першим: винести — і більше нічого в
  каталозі про це не знає.
- **`Player/Attempt/LessonProgress` — FK у каталог** (`Item`, `Paragraph`,
  `Exercise`, `SubExercise`), **але не навпаки**: каталог нічого не знає про гру.
  Винесення безпечне (однобічна залежність, без циклів), просто не перше —
  після винесення `schools` як репетиції техніки.
- **`ManualEdit` — жорстко прив'язаний до `Textbook`/`Exercise`/`SubExercise`**
  (ключ запису будується з номера вправи, сторінки, типу блоку — усе каталожне).
  Винесення коштує дорожче, ніж дає користі → лишається всередині catalog
  (рішення нижче, сесія 13).

**Висновок:** порядок винесення — `schools` → `game`. `review` не виноситься.
`education` (каталог + PDF-імпорт + review) лишається «ядром» — перейменування
в `catalog` — у беклозі (сесія 20), не в основному плані: ціна (усі таблиці
`education_*`, усі імпорти по всьому репо) не виправдана користю зараз.

## 2026-10-28 — техніка перенесення моделі між застосунками без зміни БД

Django не вимагає, щоб модель жила в тому застосунку, чиє ім'я збігається з
назвою таблиці. Таблиця визначається `Meta.db_table`, а не `app_label`. Тому
перенесення моделі `School` з `education` у новий `schools` — це:

1. У новому застосунку `schools/models.py` — та сама модель, з явним
   `class Meta: db_table = "education_school"` (та назва, яку Django вже
   згенерував і яка вже є в БД — **не змінюємо**).
2. Міграція в `education`, яка видаляє модель **лише зі стану** Django
   (`migrations.SeparateDatabaseAndState(database_operations=[],
   state_operations=[migrations.DeleteModel("school")])`) — жодного `DROP TABLE`.
3. Міграція в `schools`, яка дзеркально додає модель **лише в стан**
   (`SeparateDatabaseAndState(database_operations=[],
   state_operations=[migrations.CreateModel(...)])`) — жодного `CREATE TABLE`,
   бо таблиця вже існує.
4. `python manage.py makemigrations --check` після обох міграцій має сказати,
   що стан і факт (поточні класи моделей) збігаються — це підтвердження, що
   нічого забутого не лишилось.

Чому так, а не «просто перенести клас і перегенерувати міграції»: наївний
підхід або впустив би DROP/CREATE TABLE (втрата даних на проді), або Django
згенерував би нову таблицю з новим ім'ям (`schools_school`) і дані лишились
би в старій, нікому не видимій таблиці. `SeparateDatabaseAndState` — стандартний
документований спосіб Django саме для «модель переїхала, таблиця лишилась».

## 2026-10-28 — мертвий код, знайдений при інвентаризації (сесія 1)

- **Модель `Lesson`** (`models.py:403`, `title/content/image`) — grep по всьому
  репо (крім визначення й міграції) не знаходить жодного використання. Не плутати
  з dataclass `Lesson` у `grade_map.py` — це інша, активно використовувана річ із
  тим самим ім'ям (коментар для майбутніх сесій: перейменувати dataclass, якщо
  плутанина заважає). Видаляється в сесії 9.
- **`TheoryPractice`** — лише в `admin.py` і в `generate_item_content.py`
  (management-команда). Чи ця команда ще запускається в робочому процесі —
  невідомо на момент інвентаризації; рішення про видалення/deprecation —
  за власником, не автоматично (сесія 9).
- **`education/legacy.py` + `migrate_legacy_data`** — одноразовий інструмент
  міграції дуже старих даних. Видаляти можна лише після підтвердження, що він
  уже застосований у кожному середовищі, яке існує.
- **`map_builder.py`** робить `reverse()` на імена маршрутів старого UI
  (`grade_list`, `section_list`, `paragraph_list`, `item_list`), які `urls.py`
  тримає живими лише заради цього (коментар у `urls.py` це прямо визнає: «старий
  UI видалено (фаза 18)… бекенд-чату повідомлено, що він більше не потрібен»,
  але код досі залежить). Виправляється в сесії 10 — не мертвий код сам по собі,
  а зайва залежність, яка тримає мертвий код живим.
